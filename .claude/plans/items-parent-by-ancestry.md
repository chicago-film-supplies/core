## The defect, in one paragraph

`resolveBlock` found a line's parent as "the first row in the block with this uid". One sub-kit twice in one (destination, group) block — the 25' Extension Cord standalone and inside a Hair & Makeup Mirror; both mirror variants (each holds the cord and the power strip); Folding Chair in the Changing Tent and Pipe & Drape; Pipes Case → LED Bar three levels deep — collapsed every copy's components onto the first copy, so `validateItemUniqueness` 400'd and a hand-correct document was not a fixed point. The same "parent = some row with this uid" assumption sat in sibling code in all three repos.

## Done — Phase 1 (core)

Verified: `deno task check`, `lint`, `check:declarations`, `check:generated`, `test` (3215 passed), `audit:citations` all green; each fix reverted in isolation turned its own test red (mutation control).

- **1a.1 `resolveBlock`** (`utils/orders.ts`): candidates sharing the parent uid are ranked by longest common suffix of their identity against the line's chain, then exact length, then first occurrence — `closestAncestor` (`utils/item-pairing.ts`, exported). Path authors checked: `buildOrderComponentLines` threads the full chain; `moveLinesToLeg` (the rental-extension move helper) keeps moved rows' full stored paths. A short `[K, a]` chain against two NESTED Ks is genuinely ambiguous and falls to the first copy (pinned by a test).
- **1a.2 `rebuildFulfillmentItems` pass 2**: places a substitution after the ancestor at its PATH prefix.
- **1a.3 `carryForwardOverrides`**: pairs exact path → `(uid, component ancestry, k)` → `(uid, k)` via the new `pairItemsAcrossRebuild`; `mapPathsAcrossRebuild` now builds on it.
- **1a.4 `adoptOrderDividerStructure`**: pairs the same way with invoice paths **stripped of the order prefix** — the order uid is a FirestoreId, so `isProductShapedUid` counts it and it would sit in every invoice signature (measured: unstripped falls back to `(uid, k)` and swaps rows). Unpaired lines re-hang under the copy `closestAncestor` picks.
- **1a.5 `bookingSourceOf`**: also requires `componentSignatureHash(i.path) === parsed.signatureHash`.
- **1a.6 `getGroupPath`**: additive `productPath` (the parent's full path); `product` unchanged for templates. `template-helpers.generated.ts` regenerated byte-identical.
- **1b `@cfs/core/utils/item-rules`**: `itemArrayIssues(doc, grain, { recompute })` → `ItemArrayIssue[]` discriminated by `rule`, composing existing blocks only. `checkExchangedFor` now delegates to the pure `exchangedForViolations` (exported from `@cfs/core/schemas`; messages and issue paths unchanged). Grains: all get leading_divider, destination_join (when `destinations` given), parentage, uniqueness, path_empty, path_not_self, path_fixed_point, zero_priced_non_component, zero_priced_unstated; order adds zero_quantity_component + mixed_booking_grain; order + fulfillment add exchanged_for. Deliberately out (in the docstring): `orderLineClaimIssues`, `chargeWindowPairViolations`, the fulfillment `uid_order` agreement, product components, credit notes.
- **1c `keepKitAncestors`** (`utils/fulfillment-items.ts`): *a kept fulfillment row keeps its product ancestors* at `quantity: 0` / `quantity_ordered: 0`, matched by PATH. Lifted from `syncRows`' private loop so the invoice-only projection can share it (gap G1 below).
- Tests: `tests/items-parent-ancestry.test.ts` (1a, hand-written expectations), `tests/item-rules.test.ts` (1b, hand-written per-grain rule set), `tests/fulfillment-items.test.ts` (1c).

- Docs: the `cfs-order-projections` skill's `path_order_item` paragraph restated (the real reason is that the resync rebuilds at the order's own paths, so a carried pointer is a self-claim under any pairing key) — committed in `claude-plugins` as `1eddcaa` (1.40.4).

### Decisions taken while building

- `closestAncestor` and `pairItemsAcrossRebuild` live in `utils/item-pairing.ts`, not as file-locals: `resolveBlock` and `adoptOrderDividerStructure` are in different files and must not disagree. Both are template-denylisted with a reason.
- Zero-priced rules run on the FULFILLMENT grain too: `FulfillmentSchema` attaches `checkZeroPricedComponents` today, so the composition mirrors the schema.
- `validateItemParentage` still reads a parent's TYPE by uid. Left alone: copies sharing a uid share a type, so it cannot misjudge.
